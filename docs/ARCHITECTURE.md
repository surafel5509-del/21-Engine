# S Engine architecture

## Data, runtime and UI modules

- `engine` is pure Kotlin/JVM. `GameProject → GameScene → Entity` is a versioned, serializable scene graph; the last entity in the flat list is drawn on top. Entities have transforms, visuals, optional `PhysicsBody` components, motion settings and optional `ScriptAsset` references. A project holds multiple scenes plus metadata for image and script assets. `ProjectCodec` validates references, IDs, finite numeric values and size limits. `SceneOps` implements immutable edits and inverse-rotated hit testing.
- `WorldRunner` constructs a **fresh JBox2D world** for the current scene. It converts 100 world units to one Box2D meter, advances in fixed 1/60-second steps, and caps catch-up after frame stalls. Physics fixtures support dynamic/kinematic/static bodies, rotated boxes and circles, sensors, density/friction/restitution, velocity, gravity scaling, damping and contact callbacks. Collisions can fire `on collision` scripts on both objects; none of these mutations are saved to the edit scene. Spin/float/patrol motions are applied relative to their starting transforms. Stop discards the world; pause and step retain it for inspection.
- `ScriptProgram` parses S Script into bounded event handlers, evaluates variables/expressions, and only exposes a small `ScriptHost` API (transforms, velocity, impulses and logs). Parse errors and runtime errors appear in the console. There is no dynamic bytecode loading, `eval`, arbitrary Java/Kotlin execution, filesystem access or network API for project scripts.
- `renderer` owns `ScenePainter`, a shared native Android Canvas painter for editor and player. It draws shapes/text/sprites and optionally the grid, game frame, collider outlines and selection handles. Sprite decoding is downsampled and cached with a 16 MiB limit. In play mode, a camera-following output frame is fitted and letterboxed, matching the built player.
- `app` contains the Compose landscape editor, `StudioViewModel`, `ProjectStore`, scene viewport touch controller and SAF import/export. The hierarchy/viewport/inspector span the work area; a collapsible Console/Assets/Scripts/Build dock provides logs, asset management, script editing and export. The ViewModel owns bounded undo/redo, autosave, play/stop/pause/step and UI state.
- `player` is an independent installable Android application, **not** a screen inside the editor. It loads bundled `game/project.json` and `game/assets/<id>.img`, creates the same `WorldRunner`, uses `ScenePainter`, renders into the scene's game dimensions, and forwards taps into the runtime. A small overlay labels the game and can switch scenes when a project contains more than one. It requests only the app APIs needed to run a bundled local game; no internet/storage permission is declared.

## Coordinates and drawing

The origin of each camera's output is the center of the viewport. X increases to the right and Y down. Transforms store center position, width/height and clockwise rotation in degrees. One world unit maps to one Android dp at editor zoom 1; the player and editor's play preview instead fit the configured scene dimensions into the available screen, multiplied by camera zoom. The camera position is the world location at display center, and the game output frame follows that position. The player clips sprites outside the frame and fills the rest of the device screen with black. Scene draw order follows the entity list; hit tests traverse it in reverse. The grid spacing is 40 world units.

## Project files and asset lifecycle

In the editor, a project is stored in private app storage under `filesDir/projects/<project ID>/project.json` and `assets/<asset ID>.img`; user-supplied *folder* names are metadata shown in the dock, not untrusted physical paths. Writes use Android `AtomicFile`, and the Storage Access Framework selects imported/exported files without broad storage access. `.sengine` is a ZIP containing `project.json` and zero or more `assets/<asset ID>.img` entries. Script sources are serialized in `project.json`. Import creates a **new** local project ID rather than overwriting the source. Exporting a web game wraps the JSON, runtime and images in a different ZIP; a web ZIP cannot be re-imported as a project package.

The standalone APK builder is `tools/build_android_game.py`: it validates a `.sengine` ZIP, disallows unknown/duplicate/traversal entries and symlinks, checks references and sizes, stages only allowlisted data in ignored `player/build/stagedGame/`, optionally stages a square PNG launcher icon, and invokes Gradle with the requested package ID, label and version. Debug builds use Android's debug signing; release builds require keystore parameters provided as environment variables on the build computer. No signing material belongs in the editor app, ZIP package or repository. **A JDK and Android SDK on the build computer are required**; no APK is compiled in the phone app. CI tests the builder and builds a smoke-test player APK from a generated fixture. This build test does not install/run the APK on an emulator.

## Limits and trust boundaries

- Project JSON is limited to 2 MB; up to 32 scenes, 2,000 objects per scene, 64 scripts and 256 image references. Imported images are at most 10 MB and must decode to at most 4096 × 4096 pixels. A project archive's decompressed total is capped at 64 MB. Imports reject unknown entries and never construct a destination path from a ZIP entry name.
- Builder-side validation mirrors the format/ZIP allowlist and clears the previous game stage before accepting a new package. A game player bounds its bundled project read to 2 MB and shows a safe error view for a missing/invalid project instead of launching the editor.
- S Script has bounded script length, expression/branch depth, instruction counts and per-frame execution. A script's exposed host operations cannot open files or launch apps. Runtime logs are bounded. Project packages are still untrusted input: import/build only packages you are willing to process with native image decoders.
- HTML5 export escapes `<` in embedded JSON so user-entered text cannot close the data script tag. Its DOM uses `textContent` and Canvas drawing, not `innerHTML` or JS `eval`. The web player implements a smaller independent physics simulation; the **Android editor/player** share JBox2D and Canvas, whereas the web player does not yet have contact/sensor parity.

## Deliberate remaining scope

This implementation supports editable Android 2D projects, but **not** all of Unity's tooling or runtime: 3D meshes/materials/lights, audio mixer, sprite animation/timelines, tilemaps, prefabs, joints/collision filtering, C#/Kotlin plugins, multiplayer, cloud collaboration and on-device APK compilation are not included. These features need separate design, editor controls, serialization and regression testing; they should not be inferred from the existence of a hierarchy or inspector.
